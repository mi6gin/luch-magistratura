## Закупки

Python читает настройки `product_planning_settings` выбранного филиала: разрешение пополнения, минимальную партию, упаковку, целевое покрытие и резерв в днях. Стандартный план пересчитывается ежедневно. Период покрытия равен `max(срок поставки + 1, target_cover_days) + safety_stock_days`, максимум 366 дней. Значения из базы применяются фактически; если таблицы настроек нет, используется минимум один день после поступления заказа, без дополнительного резерва. При наличии настроек по умолчанию 45 дней покрытия и 14 дней резерва период равен 59 дням для срока поставки до 44 дней.

Количество рассчитывается по максимальному прогнозному дефициту после даты поступления нового заказа с учётом дат уже запланированных поступлений. Потерянные продажи до этой даты не переносятся как задолженность в обычный заказ. Они отдельно показываются как `expedite_required` и `expedite_quantity`: нужна ускоренная поставка или перемещение. Обычный заказ приходит через `lead_time` дней, до продаж этого дня. Величина положительного заказа доводится до минимальной партии и затем округляется вверх до упаковки. При достаточном запасе минимальная партия сама по себе не создаёт заказ.

При отключённом пополнении заказ равен нулю. При неизвестной, будущей либо устаревшей более чем на семь дней дате остатков количество для заказа также равно нулю, действие — «ОБНОВИТЬ ОСТАТКИ». Вложенное поле `planning.proposed_order_quantity` остаётся диагностическим расчётом и не включается в корзину. Ручное обновление остатка фиксирует текущую дату. Несколько складских строк суммируются; для свежести используется самая старая дата, а неизвестная или будущая дата любой строки требует обновления.

Прогноз удлиняется до нужного периода; поля `forecast_30_*` по-прежнему относятся только к первым 30 дням. Поле `safety_stock` теперь отражает резерв в днях из настроек. Бюджетная корзина сохраняет минимальную партию и кратность; сервер дополнительно проверяет их при выгрузке заказа. Интерфейс показывает причину блокировки и дату остатков.

Суммы дневных квантилей остаются сценарными ориентирами. Они не являются квантилями совокупного спроса и не гарантируют уровень сервиса. Эта граница указана в объяснении плана. Статистическая калибровка совместного распределения спроса остаётся отдельным исследованием.

## Допуск рабочего алгоритма

`apply_policy()` — общая функция преобразования прогноза для приложения и исследовательской проверки. Она сохраняет сезонный профиль, сценарии и калибровку уровня. `validate_runtime()` оценивает именно её на последнем отложенном окне локального эксперимента; будущие промо и цены из тестовых строк ей не передаются. Маршруты фиксируются на validation последнего rolling-окна. Голосование маршрутами разных окон больше не создаёт новый, неоценённый артефакт.

Результат содержит `runtime_validation` с контрактом `seasonal-profile-calibration-v1`, маршрутами, датами, числом наблюдений, фактическим объёмом и метриками рабочего алгоритма и `seasonal-robust-v1` на тех же строках. Допуск сравнивает рабочие метрики, а не метрики прямого исследовательского router. Нужны положительный тестовый объём, совпадающие маршруты и результат не хуже встроенного алгоритма по WAPE либо условной стоимости риска для risk-router. Фактический fallback входит в проверяемую функцию и учитывается в `fallback_series`.

Исследовательские метрики сохраняются отдельно. Старый кандидат без проверки рабочего пути нельзя опубликовать: нужен новый локальный эксперимент. Уже имеющиеся production-политики не переписываются автоматически. Требование трёх rolling-окон остаётся. По-прежнему публикуются только поддерживаемые локальные router-артефакты; нейросетевые checkpoint остаются исследовательскими.

## Нулевой спрос в нейросетях

Для новых запусков по умолчанию применяется `zero_inflated_lognormal_v3`: отдельная вероятность положительной продажи и логнормальное распределение положительной величины. Квантили смеси могут быть точно нулевыми, остаются неотрицательными и упорядоченными. Обучение использует likelihood смеси: бинарную составляющую наличия продажи и плотность положительной величины. Это позволяет учить вероятность продажи даже тогда, когда все три прогнозируемые квантили равны нулю.

Изменение не доказывает улучшения точности или калибровки. Проведены короткие проверки обучения, сохранения и оценки трёх архитектур на искусственной выборке с преобладанием нулей. Полный новый сравнительный эксперимент и внешняя проверка на карагандинских продажах не выполнялись.

Старые режимы `sorted_clamped_v1` и `softplus_increments_v2` поддерживаются. Старые checkpoint загружаются с записанной параметризацией. Замороженный `ml.research.study` продолжает использовать v2, а все опубликованные таблицы, веса и контрольные суммы сохранены. Их результаты относятся к старым моделям.

Для нового исследования используйте отдельный каталог:

```powershell
python ml/research_cli.py train --data path/to/data.csv.gz --manifest path/to/manifest.json --models lstm gru transformer --folds 3 --epochs 100 --patience 10 --quantile-parameterization zero_inflated_lognormal_v3 --output storage/app/experiments-v3
```

Для каждого обученного checkpoint записываются лучшая эпоха, критерий выбора и признак исчерпания бюджета. В агрегированных результатах есть `training_diagnostics`. Бюджет и модель выбираются по validation; для окончательного вывода нужен период, который не использовался при последующих изменениях метода.

## Историческая симуляция запасов

Команда принимает ежедневные ряды `id,date,sales` исследовательского формата и явно заданный начальный запас. Сравниваются недельный наивный прогноз, Croston-SBA и сезонный робастный алгоритм. Все решения используют только прошлые наблюдения; в момент решения фактические будущие продажи не доступны. Используется та же функция ограничений заказа, что и в приложении.

```powershell
python -m ml.inventory_backtest --data docs/research/full-study/data/100.csv.gz --start 2011-11-12 --end 2011-12-09 --initial-stock 20 --lead-time 7 --review-days 7 --pack-size 1 --minimum-order 1 --safety-days 0 --series 10 --output storage/app/inventory-backtest/example.json
```

Начальный запас, срок поставки, интервал пересмотра, резерв и партия являются **условиями симуляции**, а не наблюдаемыми складскими данными UCI. Поставка поступает через фиксированный срок; неудовлетворённые продажи теряются. Проверяются доля удовлетворённого объёма, потери, дни дефицита, средний остаток, заказы и баланс запаса с учётом товара в пути. Ряды с пропущенными датами и явным дефицитом в тестовом периоде исключаются. При неизвестном наличии исторические продажи служат лишь приближением спроса.

Сроки годности, списания, перемещения и денежные затраты здесь не моделируются. Результат нельзя выдавать за экономический эффект внедрения. Короткая проверка команды выполнена на десяти публичных рядах UCI.

- Четыре изолированные проверки PHP-допуска: отсутствие рабочего подтверждения, корректное подтверждение, ухудшение метрики и несовпадение маршрутов.
- PHP-синтаксис и синтаксис JavaScript проверены. Добавлены Laravel-регрессии для допуска и выгрузки неполных упаковок.

Полный Laravel/PHPUnit-прогон локально не выполнен: PHP в данном окружении сообщает `is_readable=false` для существующего `vendor/autoload.php` и не запускает bootstrap PHPUnit. Защитные проверки библиотек не отключались. Полный PHP-прогон требуется в штатном окружении/CI до слияния.
